# 3. 데이터 설계 — 투구 데이터 · 점수식 · 구단 랭킹 집계

모든 수식은 앱(`src/core/*.ts`)과 서버(`supabase/schema.sql`)에 **둘 다 구현**되어 있고, `npm run verify:sql`이 실제 PostgreSQL 16에서 두 구현을 대조합니다(§3-6).

## 3-1. 투구 데이터

### 좌표계 (포수 시점, 단위 inch)
- `plateX`: 홈플레이트 중앙 = 0, 포수 기준 오른쪽 +. `plateZ`: 지면 기준 높이.
- 판정 대상은 **플레이트 앞면을 통과하는 공 중심 (x, z)** + 타자 신장 `batterHeightCm`.

### 스키마 (`pitches`)
| 컬럼 | 설명 |
|---|---|
| `id`, `source` | `simulated`(기본) \| `licensed`(계약 데이터). `licensed`는 `license_ref` 없으면 **DB 제약으로 저장 불가** |
| `plate_x_in`, `plate_z_in`, `batter_height_cm` | 판정 입력 |
| `release_*`, `bow_*`, `pitch_type`, `speed_kph` | 연출용(비행 곡선·구종·구속). 판정에 영향 없음 |
| `edge_margin`, `abs_call` | **생성 컬럼**(서버가 계산). 클라이언트용 뷰 `pitches_public`에서는 제외 |
| `difficulty` | easy/medium/hard/controversial (아래 표) |

### ABS 존 모델 — 가정 **A1/A2** (출시 전 KBO 공개 규정으로 재확인 필요)
- 가로 17in(플레이트 폭), 세로 **타자 신장의 27.64% ~ 56.35%**, **공 반지름 1.45in** — 공의 일부라도 존에 닿으면 스트라이크.
- 2D(플레이트 앞면) 근사. 실제 ABS의 3D 통과 판정과의 차이는 경계선에서만 의미가 있고, 이는 *시뮬레이션 모드에서는 영향 없음*(우리가 정답을 정의). 실데이터 도입 시에는 공급처가 주는 **판정 결과를 그대로 사용**하고 자체 계산은 검증용으로만 쓴다.
- `edgeMarginIn` = 공 가장자리~존 경계 거리. 음수=스트라이크, 양수=볼. `|m| ≤ 0.75in`이면 "경계선(borderline)".

### 난이도 밴드 (`|edgeMarginIn|`)
| 난이도 | 범위(in) | 쓰임 |
|---|---|---|
| easy | 3.5 ~ 10 | 한 판의 1·2구 (워밍업) |
| medium | 1.5 ~ 3.5 | 3구 |
| hard | 0.5 ~ 1.5 | 4·5구 |
| controversial | 0.02 ~ 0.75 | **오늘의 논란 판정** |

한 판(5구)은 난이도 램프 + 스트라이크/볼이 **반드시 섞이도록** 생성(테스트로 30시드 검증 → 정답 편향 방지).

### 출처 정책 (제약: *라이선스 가능한 출처만, 불가하면 시뮬레이션*)
| 단계 | 사용 데이터 | 조건 |
|---|---|---|
| MVP/알파/베타 | **시뮬레이션 궤적** 100% | 화면·공유 카드·클립에 "시뮬레이션" 상시 고지(`pitch.source`로 자동). 실제 경기 영상/기록으로 오인되지 않게 |
| 개막 후 | `licensed` 추적 데이터(좌표) | KBO/KBOP 또는 추적 데이터 공급사와 **서면 계약**(재배포·가공·앱 노출 범위 명시) 후, `license_ref` 기록 |
| 그 이후 | 경기 영상/클립 | 방송권/중계사 별도 라이선스. **MVP 범위 밖** — 영상 없이 *좌표 기반 재현 애니메이션*으로 대체 |

크롤링/무단 수집 데이터는 사용하지 않는다. 구단명·색은 사용하되 **로고·엠블럼은 미사용**(상표) — 법무 확인 전까지.

### 시뮬레이션의 한계(정직하게)
- 투구 위치 분포는 정규분포 근사이며 실제 리그 분포와 다르다. 따라서 **정확도 절대값(예: 60%)은 실제 심판/타자의 능력을 의미하지 않는다.** 구단 대항전의 순위는 *앱 안에서의 상대 비교*로만 의미가 있다.
- 오늘의 논란 판정의 팬 투표는 알파 단계에서 **시뮬레이션 투표**(결정적 의사난수)다. 실제 투표 집계는 서버 `controversy_tally()`가 담당하며 화면 코드는 동일하다.

## 3-2. 점수식 (개인 점수 — 구단 순위에는 쓰지 않음)

```
score = correct ? 100 + difficultyBonus + speedBonus + comboBonus : 0
difficultyBonus = round( 100 · clamp(1 − |edgeMarginIn| / 4, 0, 1) )   # 경계선일수록 최대 +100
speedBonus      = round(  50 · clamp(1 − rtMs / 4000,        0, 1) )   # 4초 제한, 최대 +50
comboBonus      = 10 · min(연속정답 − 1, 4)                              # 최대 +40
```
- 한 구 최대 **290점**, 한 판 최대 1,450점. 오답/시간초과 0점. 논란 판정 투표는 점수 없음(정확도에만 반영).
- *왜 순위에 점수를 안 쓰나*: 속도·기기 입력 지연·난이도 운 차이가 구단 순위를 왜곡하지 않게 하기 위함(§3-3 ③).
- `.5` 경계 반올림은 SQL `numeric`과 JS 부동소수가 어긋날 수 있어 6자리 정규화 후 반올림(검증에서 1,500건 중 2건 어긋나는 것을 발견해 수정).

## 3-3. 구단 랭킹 집계 (주간 시즌)

**시즌**: 월 00:00 ~ 일 24:00 **KST**(`season_week(ts)` = KST 기준 주 시작 월요일 날짜). 시즌 종료 시 최종 순위를 스냅샷하고 다음 주는 0부터.

입력: 사용자 u의 이번 주 `(시도 n_u, 정답 c_u)` (퀴즈 + 논란 판정 투표 모두 포함).

1. **개인 캡** (헤비 유저 방지): `n'_u = min(n_u, 100)`, `c'_u = c_u · n'_u / n_u`
2. **리그 평균**: `μ = Σc' / Σn'`
3. **베이지안 수축** (소표본 구단 보호): 구단 T의 정확도
   `acc_T = ( Σ_{u∈T} c'_u + m·μ ) / ( Σ_{u∈T} n'_u + m )`, 기본 `m = 50` (가상 시도 50회)
4. **정렬**: `acc_T` 내림차순 → 참여 인원 → 구단 id. 참여자 0명 구단도 표시(리그 평균과 같은 값).
5. **잠정 표시**: 참여 인원 < 5명이면 `provisional`.

> ③ 정확도만 사용. 점수(속도·난이도)는 쓰지 않음.

**작은 예시** (μ = 0.60 가정): 한 구단에 A(100구/70정답), B(40/26), C(200/120). 캡 적용 → (100,70), (40,26), (100,60) → Σn'=240, Σc'=156 → `acc = (156 + 50·0.6)/(240+50) = 0.641` (원시 정확도 216/340 = 0.635).

**구단 기여도** = `c'_me − n'_me · μ` ("평균 팬보다 우리 구단에 정답을 몇 개 더 보탰나", 음수 가능, 소수 1자리). 예: 20구 15정답, μ=0.6 → **+3.0**.

**하이퍼파라미터(캡 100, m 50, 최소 인원 5)는 가정 A6** — 알파에서 "순위가 하루 안에 너무 요동치는가 / 너무 안 움직이는가"를 보고 조정. 캡·m은 SQL 함수 인자라서 배포 없이 바꿀 수 있다.

**실시간성**: 앱은 30초 폴링(알파). 구단 수가 10개로 고정이라 `team_ranking()`은 `answers`의 주간 파티션 인덱스(`season_week, team_id, user_id`)로 충분하다. 트래픽이 커지면 1분 단위 materialized view 또는 Realtime 채널로 전환(Phase 3).

## 3-4. 어뷰징 대응 (금전 보상이 없어 유인이 낮다는 전제)
| 위험 | 대응 |
|---|---|
| 봇/자동 풀이(좌표를 읽어 정답 계산) | 응답 시간 하한(<250ms 반복)·정확도 이상치(≥98% & 표본 ≥50) **플래그 → 집계 제외**(서버 배치). 투구를 서버가 발급/채점(베타) |
| 주중 구단 갈아타기 | `answers.team_id` 응답 시점 스냅샷 + 구단 변경은 **다음 월요일부터 적용**(`pending_team_id`) |
| 다계정 | 익명 계정 생성 레이트리밋, 캡이 개인 영향력을 100구/주로 제한 |
| 클라이언트 조작 | **알파는 클라이언트 채점(신뢰 기반)** → 베타부터 `submit_answer()` 서버 채점. `pitches` 직접 조회 금지(RLS), 정답 컬럼은 `pitches_public` 뷰에서 제외 |

## 3-5. 개인정보 / 규제 (확인 필요 항목 포함)
- **가입 없이 시작**: 익명 계정(기기 로컬 `anonId`)만 사용. 수집: 닉네임, 응원 구단, 응답 로그. 이메일/전화/위치 **미수집**. 푸시는 MVP에서 **로컬 알림**이라 푸시 토큰도 서버에 저장하지 않음.
- 10대 타깃 → **만 14세 미만 법정대리인 동의 요건(개인정보 보호법)** 확인 필요(A9). 익명·최소 수집 설계로 회피 가능한지 법무 검토. 소셜 로그인 승격 시 연령 확인 UI 필요.
- **금전 보상·베팅 금지**: 현금·상품권·경품 없음. 보상은 배지/칭호만. 순위 보상 금전화·승부예측 요소 추가 금지(제품 원칙으로 문서화).
- 구단/KBO 명칭·로고 사용 범위는 법무 확인(A3).
